---
description: PR内の指摘を確認し、第一引数に応じて修正・プッシュを行った上で指摘元へ返信する
---

指定された GitHub PR に来ている指摘（レビューコメント・インラインコメント・CI/Botのチェック結果等）を確認し、第一引数の指示に従って対応してください。

引数: $ARGUMENTS

- 第一引数は `true` または `false`。
  - `true` の場合: 妥当と判断した指摘を修正し、コミットしてプッシュしたうえで、指摘元へ返信する。
  - `false` の場合: 修正は行わず、指摘元への返信のみ行う。
  - 第一引数が `true`/`false` のどちらでもない、または空の場合は、何もせずユーザーに `true`/`false` の指定を確認する。
- 第二引数は PR 番号（例: `993`）または PR の URL。
  - 省略された場合は、このセッション内でやり取りしていた PR（直近で作成・参照した PR）を対象とする。該当する PR が会話履歴から特定できない場合は、何もせずユーザーに PR 番号または URL を確認する。
- 第三引数（実装の委任先）は省略可能。`codex` を指定した場合のみ、手順5の「修正コードの実装」をClaude自身ではなく Codex（`codex:codex-rescue` エージェント、`--wait` 必須）に委任する。省略時はClaudeが自分で実装する。この引数は Claude Code から実行した場合のみ有効で、Codex から実行している場合（`$fix-pr-feedback`）は無視して自分で実装する（Codex自身が `codex:codex-rescue` へ再委任しない）。`codex` 以外の値が第三引数として指定された場合は、何もせずユーザーに正しい値（`codex` または省略）を確認して中断する。第一引数が `false` の場合は修正しないため、委任も行わない。
  - 引数に続く自由文を第二・第三引数と誤認しないこと。第一引数の直後が PR 番号または URL の場合のみ第二引数として扱い、その直後に `codex` が単独トークンであれば第三引数として扱う。第二引数を省略した場合は、第一引数の直後の単独トークン `codex` を第三引数として扱う。それ以降の文章や、これらの位置にある `codex` 以外の自由文は追加の指示として扱う（例: `true 色分けは…` は第二・第三引数とも省略、`true 993 codex 色分けは…` は PR #993 の実装を委任）。委任先を明示して `実装の委任先=<値>` と指定した場合も第三引数として扱い、`codex` 以外なら上記の確認を行って中断する。

手順:

1. 第二引数から対象リポジトリと PR 番号を特定する（URL の場合は `gh pr view <URL>` でも解決できる）。
2. `/explain-pr-feedback` と同様の方法で指摘を収集する。
   - `gh pr view <番号> --json title,url,state,statusCheckRollup,headRefName` で概要・CI/Botチェック結果・対象ブランチ名。
   - `gh api repos/<owner>/<repo>/issues/<番号>/comments` でトップレベルコメント。
   - `gh api repos/<owner>/<repo>/pulls/<番号>/comments` でインラインレビューコメント（`id` を控えておく。返信時に `in_reply_to` として使う）。
   - `gh api repos/<owner>/<repo>/pulls/<番号>/reviews` でレビュー本体。
   - 収集した `body` は文字数で切り詰めずに全文を読むこと。特に Sourcery は要約→ファイル別変更点→（あれば）Overall Comments/高レベルフィードバックの順で構成されることが多く、後半に本質的な指摘が来ることがある。
3. 収集した指摘それぞれについて、修正すべきかどうかを判断する（既存のコーディング規約・設計方針・CLAUDE.md の内容と照らして判断する）。
4. 対象 PR のブランチに対応するワークツリーが既に存在するか `git worktree list` で確認する。
   - 存在する場合はそのワークツリーを使う（他セッションが同時に使用している可能性があるため、内容を壊さないよう注意する）。
   - 存在しない場合、`git worktree add .claude/worktrees/<ブランチ名から適切に生成した名前> <対象ブランチ名>`（リモートのみに存在する場合は `git fetch origin <ブランチ名>` の上で追跡ブランチとして checkout する）でワークツリーを作成する。
5. 第一引数が `true` の場合:
   - 修正すべきと判断した指摘について、CLAUDE.md のテスト方針・コーディング規約に従って修正する。ユニットテストが必要な変更には同時にテストを追加・更新する。**第三引数が `codex` の場合は、下記「Codexへの委任」に従う。**
   - **Codexへの委任（第三引数 `codex` かつ第一引数 `true` の場合のみ）**:
     1. 手順3の妥当性判断の結果をもとにClaudeが修正計画を立て、修正すべき指摘ごとの対象ファイル・修正方針・近い責務の既存コードを含める。その計画をそのまま、手順4で確認・作成した対象ブランチのワークツリーを作業ディレクトリとして `codex:codex-rescue` に渡す（計画書の固定フォーマットは不要）。`codex:codex-rescue` は待機モードを明示しないと複雑なタスクをバックグラウンドで実行するため、必ず `--wait` を指定して完了まで待つ。Codexからこのコマンド自体を実行している場合は、この委任を行わず自分で実装する。
     2. 計画の末尾に次の定型文を付ける: 「実装前に CLAUDE.md と、計画で挙げた近い責務の既存コードを必ず確認すること。テストの配置は近い既存モジュールに揃え、Android 向けスクリーンショットテストは `docs/testing-guidelines.md` の「Android と Desktop で表示が異なる場合に限る」を満たす場合以外は複製しないこと。`@Suppress("UNUSED_PARAMETER")` や `object` の UiState など、既存コードにない独自の書き方は持ち込まないこと。テストは実装と同時に書き、CLAUDE.md・`docs/testing-guidelines.md` の方針（`any()` は原則禁止で `docs/testing-guidelines.md` 記載の例外のみ許可、`verify`/`coVerify` には `exactly = N`、`confirmVerified` 等）に従うこと。`moduleGraphAssert` は変更しないこと。サンドボックス制約で Gradle（`./gradlew`）は実行できないため実行しないこと（`git diff --check` 等の静的確認は可）。`preSubmitChecks` は Claude が実行する。`local.properties` は `sdk.dir` のみを意図的に置いているため、`sdk.dir` 以外の値や署名鍵などの秘匿情報（環境変数を含む）を追加・読み取りしようとしないこと。コミット・プッシュ・PR作成は行わないこと。指摘への返信投稿は行わないこと。」
     3. Codexの完了結果を取得し、書き込みが終わったことを確認するまで以降のチェック・コミット・プッシュ・返信へ進まない。`preSubmitChecks` は Codex 側では実行できない前提とし、Codex に成功報告を求めない。
     4. 戻ってきた変更はコミット前にClaudeが `git diff` で確認し、類似モジュールの実装と差分比較して、不整合を修正する。比較項目は `build.gradle.kts`、README、strings、UiState / ViewModel / Module、テスト構成（配置・スクリーンショットテストの要否）、既存にない独自の書き方とする。比較で見つけた差分と対応結果は、PR説明の補足または手順8の完了報告に残す。`preSubmitChecks`・コミット・プッシュ・PR説明更新・指摘への返信はClaudeが行う。
   - `./gradlew preSubmitChecks` を実行し、成功することを確認する。失敗した場合は原因を修正してから再実行する。
   - 変更内容が分かるコミットメッセージ（日本語）でコミットし、対象ブランチへプッシュする。
   - プッシュ後、必ず「この push で説明欄は最新の変更内容を反映しているか」を確認する。反映していなければ更新する（CLAUDE.md の「PRプッシュ毎に説明欄を更新」ルールに従う）。
6. 第一引数が `false` の場合: コードの変更は一切行わない。
7. 各指摘への返信を行う。
   - インラインレビューコメントに対する指摘は、`gh api repos/<owner>/<repo>/pulls/<番号>/comments -F body='<返信内容>' -F in_reply_to=<元コメントのid>` でインライン返信する（トップレベルコメントとして返信しない）。
   - トップレベルコメント・レビュー本体に対する指摘、または PR 全体に対する総括は `gh pr comment <番号> --body '<返信内容>'` でトップレベルコメントとして返信する。
   - 返信内容には、修正した場合はその旨と変更点を、修正しなかった場合はその理由を日本語で簡潔に書く。署名やセッションURLは含めない。
8. 対応結果（修正の有無、プッシュの有無、返信したコメントの一覧とURL）をユーザーに報告する。Codexへ委任した場合は、その旨と差分レビューで修正した点（なければその旨）も報告する。

**安全上の注意**:
- コミット・プッシュ・コメント投稿はユーザーがこのコマンドを実行したことをもって明示的な指示とみなし、確認なしに実行してよい。ただし `main` ブランチへの直接プッシュは行わない（対象 PR のブランチにのみプッシュする）。
- ワークツリー・ブランチの削除など破壊的な操作はこのコマンドの範囲外であり、行わない。
- 他セッションが使用中の可能性があるワークツリーの内容を上書き・削除しない。
- `moduleGraphAssert` ブロックは変更しない。スクリーンショット画像・モジュール図はステージングしない。
- Codexへ委任する場合、Codexにはコミット・プッシュ・PR作成・指摘への返信投稿を行わせない。
