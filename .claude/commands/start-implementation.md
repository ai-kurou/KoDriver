---
description: 実装内容とベースブランチを指定して、専用ワークツリー・ブランチを作成し実装からPR作成・CI完了待ち・PR指摘の要約報告まで一気通貫で行う
---

第一引数を「実装内容」、第二引数を「ベースブランチ」として受け取り、作業用ワークツリーとブランチを作成したうえで実装に着手し、コミット・プッシュ・PR作成、CIの完了待ち、PRに来ている指摘の要約報告までを一気通貫で行ってください。

引数: $ARGUMENTS

- 第一引数（実装内容）が空の場合は、何もせず実装内容を確認するようユーザーに促して終了する。
- 第二引数（ベースブランチ）が空の場合は `main` をデフォルトとして扱う。

## 実装フェーズ

1. リポジトリのルート（`git rev-parse --show-toplevel`）に移動し、`git status --porcelain` で作業ツリーがクリーンであることを確認する。未コミットの変更が残っている場合は、削除・上書きせずユーザーに報告して中断する。
2. 指定されたベースブランチを最新化する（`git fetch origin <ベースブランチ>` の上で、ベースブランチが `main` などリモート追従ブランチであれば `git pull` してよい。ローカルにしか存在しない場合はそのまま使用する）。存在しないベースブランチが指定された場合は、削除・作成などを行わずエラーを報告して終了する。
3. 実装内容から簡潔で分かりやすい英語の kebab-case のブランチ名を提案する（例: 実装内容が「終了確認ダイアログを削除する」なら `feature/remove-exit-confirmation-dialog` のように、変更の性質に応じて `feature/` `fix/` `chore/` などの prefix を付ける）。
4. `.claude/worktrees/<ワークツリー名>` にワークツリーを作成する。ワークツリー名はブランチ名から `feature/` 等のprefixを除いたものを使う。
   - `git worktree add .claude/worktrees/<ワークツリー名> -b <ブランチ名> <ベースブランチ>`
   - 既に同名のワークツリーやブランチが存在する場合は、上書き・削除せずユーザーに報告して終了する。
5. 作成したワークツリーに移動し、CLAUDE.md の「実装前」チェックリストに従う。
   - 既存実装を確認する（対象モジュールの README・近い責務の既存コードを `rg` 等で調査）。
   - 実装対象のモジュール・依存方向が妥当かを確認する。
   - 追加・変更するテストの対象を洗い出す。
6. 受け取った「実装内容」に基づいて実装を進める。CLAUDE.md のテスト方針・コーディング規約・Git操作ルールに従うこと。特に以下を厳守する。
   - `moduleGraphAssert` ブロックは変更しない。
   - スクリーンショット画像・モジュール図はステージングしない。
7. CLAUDE.md の「完了前」チェックリストに従い、`./gradlew preSubmitChecks` を実行して問題を解消する。ベースブランチが `main` 以外の場合や、ユーザーが別途「コミットしない」「PRだけ作る」等の条件を指定している場合は、その指示を優先する。
8. `docs/improvement-ideas.md` を確認し、今回実装した内容に該当する項目が既に記載されていないか確認する。該当する項目がある場合、CLAUDE.md の「`docs/improvement-ideas.md` に内容を追加・変更する場合は、事前にユーザーの承認を得ること」に従い、その項目を削除してよいかユーザーに確認する。承認が得られた場合のみ、該当項目を削除し、`docs/resolved-improvement-ideas.md` に1行（`- YYYY-MM-DD 一言サマリ（関連PR #番号）`形式）追記する（他の項目や、今回のタスクと無関係な部分は変更しない）。ユーザーから確認を得られない・保留された場合は削除せず現状のまま進める。

## コミット・PR作成フェーズ

9. CLAUDE.md の Git 操作ルールに従い、feature ブランチでのコミット・プッシュ・PR作成はユーザーの明示的な指示を待たずに自発的に実行する（`main` への直接コミット・プッシュのみ、実行前に必ずユーザーに確認する）。
   - わかりやすい日本語のコミットメッセージでコミットする。手順8で `docs/improvement-ideas.md` を削除した場合は、実装本体と同じコミットまたは別コミットのいずれでもよいが、`docs/resolved-improvement-ideas.md` への追記も含めて同じ PR に含める。
   - `git push -u origin <ブランチ名>` でプッシュする。
   - `gh pr create --base <ベースブランチ> --head <ブランチ名> --title --body` でPRを作成する。タイトル・説明は日本語で書き、署名やセッションURLは含めない。
   - PR作成後、CodeRabbit に手動でレビューを依頼する（このリポジトリはGitHub star数が少なく自動レビューが起動しないため）。PR作成直後に投稿される CodeRabbit の初回コメント本文には `- [ ] <!-- {"checkboxId":"..."} --> 🔍 Trigger review` というチェックボックスが含まれているため、そのコメントを `gh api repos/<owner>/<repo>/issues/<PR番号>/comments` で取得し、該当行のみ `- [ ]` を `- [x]` に置換した本文で `gh api -X PATCH repos/<owner>/<repo>/issues/comments/<コメントID> -f body=<書き換えた本文>` を実行してチェックを入れる（`checkboxId` はコメントごとに異なる動的な値のため、都度本文から抽出すること。該当行以外は変更しない）。

## CI完了待ちフェーズ

10. `gh pr checks <PR番号>` でCIステータスを確認する。pending のチェックが残っている場合は、`ScheduleWakeup` で妥当な間隔（数分程度）の待機を予約し、同じ確認を行う `prompt` を渡して再開する。全チェックが完了する（成功・失敗を問わない）までこれを繰り返す。

## PR指摘の要約報告フェーズ

11. CIが完了したら、対象PRについて以下の情報を収集する。
    - `gh pr view <番号> --json title,url,state,statusCheckRollup` で概要と CI/Bot チェックの結果。
    - `gh pr view <番号> --comments` または `gh api repos/<owner>/<repo>/issues/<番号>/comments` でトップレベルコメント（CodeRabbit・Sourcery・SonarQube・Codacy 等のボットコメントを含む）。
    - `gh api repos/<owner>/<repo>/pulls/<番号>/comments` でインラインレビューコメント。
    - `gh api repos/<owner>/<repo>/pulls/<番号>/reviews` でレビュー本体（Approve/Request changes 等）。
12. 収集した指摘それぞれについて、以下を整理してユーザーに報告する。
    - 指摘の内容（何を指摘しているか、インライン/トップレベルの別、対象ファイル・行）。
    - その指摘が妥当か（既存のコーディング規約・設計方針・CLAUDE.md の内容と照らして判断する）。
    - 修正すべきかどうかの結論と理由（例: 「このPRのスコープ外」「既存パターンと矛盾する」「妥当な指摘なので修正すべき」等）。
13. 指摘が存在しない場合、またはすべて「対応不要（情報のみ・Bot要約のみ等）」の場合はその旨を報告する。
14. このフェーズでは収集・分析・報告のみを行い、指摘への対応（コード修正・返信投稿）は行わない。ユーザーから別途「返信して」「修正して」等の指示があった場合のみ、そのときの指示に従って別作業として対応する。

**安全上の注意**: このコマンドはワークツリー・ブランチの新規作成、feature ブランチへのコミット・プッシュ・PR作成、PRへの調査・報告を行う。既存のワークツリー・ブランチ・コミット履歴を削除・上書きしない。他セッションが使用中の可能性があるワークツリーには一切触れない。`main` への直接コミット・プッシュは必ず事前にユーザーへ確認する。PRへのコメント投稿・マージ・修正コミットの追加は、ユーザーから別途指示があるまで行わない。
