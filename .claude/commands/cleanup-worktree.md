---
description: PRがマージ済みであることを確認したうえで、ワークツリーとブランチを削除する（引数省略時は現在のワークツリー、指定時はPR番号/PR URL/ブランチ名で対象を指定できる）
---

対象の git worktree とブランチを、対応する GitHub PR がマージ済みであることを確認したうえで削除してください。

引数: $ARGUMENTS

- 引数が省略された場合は、これまで通り**現在の作業ディレクトリ**に対応するワークツリー・ブランチを対象にする。
- 引数が指定された場合は、それを PR 番号（例: `993`）・PR の URL（例: `https://github.com/<owner>/<repo>/pull/993`）・ブランチ名（例: `feature/xxx`）のいずれかとして解釈し、対応するワークツリー・ブランチを対象にする。

手順:

1. 引数の有無で対象ブランチ・対象ワークツリーパスの特定方法を分ける。
   - **引数が省略された場合**: `git rev-parse --show-toplevel` で現在のワークツリーのパスを、`git branch --show-current` で現在のブランチ名を確認する。
   - **引数が指定された場合**:
     - 数字のみ、または PR の URL 形式であれば PR 番号/URL として扱い、`gh pr view <引数> --json number,url,headRefName` でブランチ名（`headRefName`）を取得する。PR が見つからない場合は削除を行わず、その旨を報告して終了する。
     - 上記に該当しない場合はブランチ名として扱う。
     - 特定したブランチ名を使い、`git worktree list --porcelain` の出力からそのブランチに対応するワークツリーのパスを探す。見つからない場合（既にワークツリーが存在しない、または他のブランチ用ワークツリーしかない）は、削除を行わずその旨を報告して終了する。複数のワークツリーが同じブランチに紐づいている場合（通常は発生しないはずだが）は、どれか一つに自動で絞り込まず、候補のパスを一覧でユーザーに提示し、対象を指定してもらってから次の手順に進む。
2. 直前のタスクがCI待機中（`ScheduleWakeup` でPRのCIチェック完了待ちを予約している状態）であれば、片付けを進める前に `ScheduleWakeup` を `stop: true` で呼び出し、そのループを停止する。
3. 対象のワークツリーパスが `.claude/worktrees/` 配下であることを確認する。**メインの作業ツリー（リポジトリ直下）は対象にしない。** メインツリーだった場合は何もせず、その旨を報告して終了する。
4. **引数が指定された場合に限り**、対象ワークツリー・ブランチがこのセッションで作成したものかどうかを、この会話のやり取り（`git worktree add` を実行した記録など）から確認する。このセッションで作成したことを確認できない場合は、削除を行わず「このセッションが作成したワークツリーか確認できないため、削除してよいかユーザーに確認する」旨を報告し、ユーザーの明示的な許可を得てから手順5以降に進む。
5. `gh pr list --head <branch名> --state all --json number,state,url` （または手順1で PR 番号が判明していれば `gh pr view <番号> --json state,mergedAt,mergeCommit`）で、このブランチに紐づく PR のマージ状態を確認する。
   - PR が見つからない、または `state` が `MERGED` でない場合は、削除を行わずに現在の状態を報告して終了する（`CLOSED` の場合もユーザーに確認を促し、勝手に削除しない）。
6. マージ済みであることを確認できたら、対象ワークツリーで `git status --porcelain`（または `git -C <ワークツリーのパス> status --porcelain`）を実行し、対象ワークツリーがクリーンであることを確認する（未コミットの変更があれば削除前にユーザーへ警告し、中断する）。確認できたら、メインの作業ツリー（リポジトリのルート）に `cd` してから以下を実行する。
   - `git worktree remove <ワークツリーのパス>`
   - `git branch -d <ブランチ名>`（force ではなく `-d` を使い、未マージのコミットが残っていれば失敗させる。失敗した場合は原因を報告してユーザーに判断を仰ぐ）
   - `git worktree remove` 実行後も対象パスにディレクトリが残ることがある（`.gradle` / `.idea` / `build-logic` のビルドキャッシュなど、gitignore対象でgit管理外のファイルが残っていると、gitはワークツリー登録の解除のみ行いディレクトリ自体は削除しない）。この場合、残っているディレクトリの中身を確認し、ソースコード等の追跡対象ファイルが含まれておらず、ビルドキャッシュ・IDE設定等のgit管理外ファイルのみであることを確認できたら `rm -rf <ワークツリーのパス>` で削除する。追跡対象ファイルが含まれている、または内容に確信が持てない場合は削除せずユーザーに報告する。
7. リモートブランチ（`origin/<ブランチ名>`）も削除する。`git push origin --delete <ブランチ名>` を実行する。既に GitHub 側の自動削除設定等でリモートブランチが存在しない場合は、エラーを無視してその旨を報告する。
8. 孤児化したCodexプロセスの掃除を行う。
   - このセッションがCI待機中・Codex委任の実行中でないことを確認してから行う。実行中のCodexタスクを中断する可能性がある場合は、掃除を行わずその旨を報告する。
   - メインの作業ツリーから `scripts/cleanup-codex-orphans.sh --worktree <手順6で削除したワークツリーの絶対パス>` を実行する（パスに空白がある場合は引用符で囲む）。対象を事前確認する場合は `--dry-run` を付ける。
   - スクリプトは親PIDが1の node broker のうち、経過1時間以上、または `--cwd` が指定したワークツリーパスと完全一致するルートとその子孫のみを対象にする。削除したワークツリー用のbrokerは経過時間に関係なく対象とし、`CodexBar.app` は除外する。対象ルート数・総数を表示し、各PIDのコマンドが記録時と一致することを送信直前に確認してTERM、3秒後に残存対象へKILLを送る。
   - スクリプトが出力する終了ルート数・終了総数・残存 codex プロセス数を確認して報告する。対象ルートがない場合は終了数を0として報告する。
9. 削除したワークツリーのパス、削除したローカル・リモートブランチ名、確認した PR 番号・URL、および終了したCodexプロセス数（ルート数・総数）と残存 codex プロセス数を報告する。
10. 次の実装候補を提示する（情報提供のみ。自動で着手しない）。
   - 手順5で確認した PR の `baseRefName`（`gh pr view <番号> --json baseRefName`）が `feature/base/*` の場合のみ行う。`main` 向けの単発PRなど、それ以外の場合はこの手順をスキップする。
   - `docs/roadmap/` 配下から、先頭の `base-branch:` がそのベースブランチと一致するファイルを探す。見つからない場合は「このベースブランチにはロードマップがありません」と報告して終了する。
   - 見つかった場合は、ロードマップの「次以降」の未チェック先頭から1〜3個を、直前にマージした PR との関係とあわせて提示する。「実装済み」にそのPRが未反映ならその旨も伝え、ロードマップの更新を促す。「未決事項」の確認が先に必要な候補には、その旨を明記する。
   - 判断に迷う場合は `git log main..origin/<ベースブランチ> --oneline` で実装済みの履歴を確認し、ロードマップと食い違う点を報告する。

**安全上の注意**: 自分（このセッション）が作業していたワークツリーのみを対象とすること。引数でPR番号・URL・ブランチ名を指定した場合でも、このセッションが作成したものであることを確認できない限り、ユーザーの明示的な許可なしに削除しないこと。他のセッションが並行して使用している可能性がある他のワークツリーには一切触れないこと。`git worktree remove` や `git branch -d` 以外の破壊的操作（`--force`, `-D`, `git worktree remove --force` 等）は使わないこと。
プロセス掃除は手順8のスクリプトで限定条件に合致する対象ルートとその子孫のみ許可し、それ以外のプロセスは終了しないこと。ワークツリー・ブランチ操作の `--force` 等の禁止とは別に、この限定条件内でのTERM・KILL送信は許可する。
