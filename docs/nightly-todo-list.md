# Nightly TODO List

毎晩 JST 午前5時ごろ、Claude Code がこのファイルを読み取り、内容を GitHub Issueとして起票する運用メモです。

## 使い方

- ここに、GitHub Issueとして起票したい改善案・気になっていることを箇条書きで書いておく。
- 粒度はGitHub Issueと同じく「対象・課題・改善案」がわかる程度でよい。
- 「毎晩実行する項目」「曜日ローテーション項目」は毎晩・毎週繰り返しチェックする恒常的な項目のため、処理後もこのファイルから削除しない。
- 1晩に実施するのは「毎晩実行する項目」＋「その曜日のローテーション項目」までとし、リスト全体を一度に処理しようとしない（コンテキスト・使用量超過を防ぐため）。
- Webサイトを元にした改善案をIssueとして起票する場合は、参考にしたURLも併記する。
- 外部サイト・フィードが取得できない（403・タイムアウト等）場合は、その項目を「取得不可（URLと理由）」として最終出力に記録し、他の項目の調査を続けます。これだけで全体を未完了（blocked）扱いにはしません。
- Issueとして起票する前に、`gh issue list --search` でオープン・クローズ問わず同趣旨のIssueが既に存在しないか、また対象のコードを実際に読んで既に修正済みでないかを確認する。
- 改善案は「〜が気になる」のような抽象的な記述ではなく、対象のファイルパス・関数名・クラス名など具体的な箇所を必ず含める。
- 夜間バッチが起票するIssueは、他の作業と競合していないか（同じ箇所を対象にした未マージの PR やオープン中のIssueが既にないか）を、人間側でレビュー時に確認する。

## 毎晩実行する項目

- 対象キーワードは共通で「Compose・Android・Claude・Codex・Kotlin」とする。以下のZenn・Qiita双方とも、まずキーワードで検索してから過去24時間以内かを判定する（新着記事を全件取得してからキーワードでフィルターする方式は使わない。取得件数・処理量を減らすため）。
- 記事をIssue起票対象として拾うかどうかは、以下の軸を満たすかで判断する。
  - **KoDriverへの適用可能性**: 記事の内容をKoDriverのコード・設計・運用にそのまま、または応用して取り入れられるか。
  - 単に技術的に興味深い・一般的に有用というだけでは起票しない（「[調査メモ]」のような、KoDriverへの具体的な適用先を持たない知見メモ的Issueが乱立したため、この軸は廃止した）。
- Zenn: キーワードごとに `WebFetch` で `https://zenn.dev/api/articles?topicname=<topicname>&order=latest&count=100`（Zennが公開しているトピック別記事一覧のJSON API）を取得する。`topicname` は各キーワードに対応するZennのトピック名（`compose`, `android`, `claude`, `codex`, `kotlin`。いずれもキーワードを小文字化したもの。「Compose Multiplatform」は独立したトピックが存在しないため`compose`で代用する）を指定する。`count=100` で足りない場合は `next_page` を参照して `page=2`, `page=3`, ... と進める。トピックによる絞り込みのため無関係な記事が混じることがあるが、タイトルからの関連性判断は次のステップに委ねてよい。取得した記事の中から `published_at` が24時間以内のものだけを対象にし、上記の判断軸（KoDriverへの適用可能性）を満たすとClaudeが判断したものがあればIssueとして起票する。`WebSearch`はZennの新着記事のインデックス反映が遅く投稿直後の記事を拾えないことが分かっているため使わない。
- Qiita（[https://qiita.com](https://qiita.com)）: キーワードごとに `WebFetch` で `https://qiita.com/api/v2/items?query=<キーワード>+created:%3E%3D<24時間前の日付、JST基準でYYYY-MM-DD形式に丸めたもの>&page=1&per_page=100`（Qiita API v2の記事検索、`query`パラメータでキーワード検索し`created:>=`で日付範囲を絞り込む）を取得する。`created:>=`は日付単位（時刻は含まない）で指定し、JST基準で「24時間前の日付」に丸めた日付を使う（境界日の記事が漏れなく含まれるよう、日付の切り上げは行わない）。1回のレスポンスが100件（`per_page`の上限）に達した場合は、対象キーワードで24時間以内の記事を取りこぼさないよう `page=2`, `page=3`, ... と進めて取得を続ける。取得した記事のうち `created_at` が実際に過去24時間以内のものだけを対象にし、上記の判断軸（KoDriverへの適用可能性）を満たすとClaudeが判断したものがあればIssueとして起票する。
- Zenn・Qiitaいずれも、絞り込み対象になった記事・ならなかった記事を問わず、過去24時間以内に取得できた全記事のURLと1行程度の要約を、最終出力（ワークフローのジョブサマリーに転記される）に一覧として必ず含める。ただし全件網羅（個別記事の内容まで深掘りする）は不要で、タイトルから明らかに関連しそうな記事だけを深掘りすればよい。深掘り要否の判断では、記事本文の`liked_count`（Zenn）・`likes_count`（Qiita）を参考にしてよい。3未満の場合はタイトルから見て判断軸（KoDriverへの適用可能性）に明確に該当すると判断できるときだけ深掘りし、それ以外は要約一覧への記載のみに留めて深掘りを省略する（投稿から24時間以内の記事はいいねが伸びる前の段階のため、いいね数だけで機械的に対象外とはしない）。
- Android Developers Blog: `WebFetch` で `https://developer.android.com/static/blog/atom.xml`（2026-10 にBloggerから `developer.android.com/blog` へ移行した公式のAtomフィード）を取得し、各 `<entry>` の `<published>` が過去24時間以内の記事だけを対象にする。更新頻度が不定期なため曜日ローテーションではなく毎晩確認する。対象記事のうち、KoDriverが取り入れていない・遅れている技術やプラクティスで採用価値があると上記の判断軸（KoDriverへの適用可能性）で判断したものがあればIssueとして起票する。過去24時間以内に該当記事がなかった場合もその旨を最終出力に含める。
- Android Developers Japan Blog: `WebFetch` で `https://android-developers-jp.googleblog.com/feeds/posts/default?alt=json&max-results=5`（Android Developers Blogと同じBloggerのフィードJSON API）を取得し、`published` が過去24時間以内の記事だけを対象にする。更新頻度が不定期なため曜日ローテーションではなく毎晩確認する。本家Android Developers Blogの日本語版・意訳のため内容が重複することが多いが、日本語版のみで先行公開される記事もあるため独立して確認する。対象記事の判断基準・Issue起票要否はAndroid Developers Blogと同様（上記の判断軸〈KoDriverへの適用可能性〉を満たすか）。過去24時間以内に該当記事がなかった場合もその旨を最終出力に含める。
- Kotlin Blog: blog.jetbrains.com は `WebFetch` が403になる場合があるため、先に `WebFetch` で `https://github.com/JetBrains/kotlin/releases.atom`（Kotlinのリリース情報のAtomフィード）を取得し、過去24時間以内のリリースを確認します。そのうえで `WebFetch` で `https://blog.jetbrains.com/kotlin/feed/`（JetBrains公式KotlinブログのRSSフィード）も取得を試み、各記事の公開日時が過去24時間以内のものだけを対象にします。403の場合はURLと理由を「取得不可」として最終出力に記録し、blockedにはしません。更新頻度が不定期なため曜日ローテーションではなく毎晩確認する。対象記事のうち、Kotlin言語仕様・KotlinコンパイラやGradleプラグインの変更で `libs.versions.toml` の更新余地がある、または上記の判断軸（KoDriverへの適用可能性）を満たすものがあればIssueとして起票する。過去24時間以内に該当記事がなかった場合もその旨を最終出力に含める。
- はてなブックマーク テクノロジーカテゴリ: `WebFetch` で `https://b.hatena.ne.jp/hotentry/it.rss`（テクノロジーカテゴリの人気エントリーRSS）を取得する。このRSSはブックマーク数に基づく人気順であり掲載日時の絞り込みができないため、過去24時間以内の判定は行わず、取得できた上位記事全体を対象にタイトルから明らかにCompose・Android・Claude・Codex・Kotlin・KoDriverの技術領域に関連しそうなものだけ深掘りする。対象記事のうち上記の判断軸（KoDriverへの適用可能性）を満たすものがあればIssueとして起票する。該当記事がなかった場合もその旨を最終出力に含める。

## 曜日ローテーション項目

- 月: プロジェクト全体を見て、バグ・不具合・配線漏れ（例: ReadoutItemKeyがlistPaneにはあるがNarrator側で未参照など）・仕様不備があればIssueとして起票する。 / アニメーション付与、識別しにくい配色の変更、GUI配置の見直し、マテリアルデザインからの逸脱など、UI/UXの改善提案があればIssueとして起票する。 / `AndroidDataModule.kt`（`core:data`）・`DesktopDataModule.kt`（`core:data`）と、それらが `includes(...)` で束ねるシミュレーター別ファイル等のKoin DIモジュールを確認し、新設したRepository/UseCaseの`single { }`バインディングが漏れていないか（片方だけ実装してもう片方への配線を忘れる、ReadoutItemKeyの配線漏れと同種のバグパターン）があればIssueとして起票する。 / Androidダガシ🌰（[https://androiddagashi.github.io/](https://androiddagashi.github.io/)）は毎週日曜午後に新しい記事が公開されるため、月曜のこの項目で最新記事をWebで確認する。取り上げられているトピックの中でKoDriverに関連しそうなもの（Compose Multiplatform、Kotlin、Jetpack、Android開発全般の新機能・プラクティス等）があれば、参考記事のURLとあわせてIssueとして起票する。
- 火: `libs.versions.toml` に記載の各ライブラリについて最新安定版をWebで確認し、致命的な不具合がない範囲で更新余地があればIssueとして起票する（CLAUDE.mdの「ライブラリバージョン管理」方針に沿う）。 / `./gradlew koverXmlReport` の結果を確認し、カバレッジ100%方針から外れているのに除外理由が妥当でない箇所があればIssueとして起票する。
- 水: detekt・ktlintを実行し、エラーには至っていないが閾値（LongMethod・CyclomaticComplexMethod等）に近づいている箇所があればIssueとして起票する。 / `rg` 等で未使用のクラス・関数や、複数モジュールに散らばった重複実装がないか横断的に確認し、あればIssueとして起票する。 / `@Composable` 関数で不要な再コンポジションを招きやすい実装（`remember`/`derivedStateOf` の使い所、`Stable`/`Immutable` の付与漏れ、ラムダ・オブジェクトの再生成など）がないか確認し、あればIssueとして起票する。
- 木: 認証・暗号化なしで稼働しているKtorサーバー（`0.0.0.0:8080`）まわりなど、既知の制約以外に新たなセキュリティリスクが増えていないか確認し、あればIssueとして起票する。CLAUDE.mdに記載の既知の制約（認証なし・LAN限定）は新規リスクとして起票しない。 / `server/` 配下を Grep で `webSocket(` と `telemetryWebSocketRoute` を検索し、Origin拒否（CSWSH対策）を行う `telemetryWebSocketRoute` を経由せず `webSocket(` を直接呼んでいるWebSocketルートがないか確認する。あわせて配信するJSONのシリアライズ対象（データクラス）を読み、端末識別子・ユーザー名・ホスト名など不要な個人情報が含まれていないか確認し、あればIssueとして起票する。 / `KoDriverServer.start()` 周辺を Grep で `_kodriver._tcp.local.` と `TXT`（`txt` を含む大文字小文字不問）で検索し、mDNS広告のTXTレコードにホスト名・ユーザー名など想定外の情報が載っていないか確認し、あればIssueとして起票する。 / `gradle/libs.versions.toml` の Ktor（`ktor`）・Netty（`ktor-serverNetty` の依存先）・kotlinx-serialization（`kotlinx-serialization`）等の主要ライブラリについて、現行バージョンに該当する既知の脆弱性がないか、`gh api repos/<owner>/<repo>/security-advisories`（例: `repos/ktorio/ktor/security-advisories`、`repos/Kotlin/kotlinx.serialization/security-advisories`、`repos/netty/netty/security-advisories`）で GitHub Security Advisories を確認し、あればIssueとして起票する。 / `.github/workflows/*.yml` を Grep で確認し、各ワークフローの `permissions` が最小権限になっているか、`pull_request_target` を使用している箇所がないか、`uses:` がコミットSHAで固定されていない（`@v4` 等のタグ指定の）箇所がないか確認し、あればIssueとして起票する。 / `README.md`・`docs/` 以下・テストフィクスチャを Grep で `STORE_PASSWORD`・`password`・`secret`・`token`・`local.properties` 等の秘匿情報らしき文字列で横断確認する（`local.properties` の中身は読まず、`sdk.dir` 以外の値を含む記述が文書やフィクスチャに混入していないかのみを対象とする）。混入があればIssueとして起票する。 / displayNameやUI文言（表示名・ラベル・エラーメッセージ等）に表記揺れがないか横断的に確認し、あればIssueとして起票する。確認は Grep で全角/半角の混在（英数字・記号・カタカナ語）、送り仮名の違い（例: 「読み込み」と「読込」、「引き継ぎ」と「引継ぎ」など）、用語の不統一（例: 「ラップ」と「周回」、「ラップタイム」と「ラップ時間」など）を対象キーワードごとに検索して行う。
- 金: `assertModuleGraph` は通っていても、本来分離すべき責務が同一モジュールに混在していないかなど、依存関係グラフの設計面での気になる点があればIssueとして起票する。 / ルートの `CLAUDE.md`（モジュール構成表など）や各モジュールの `README.md` が実際の実装から乖離していないか（モジュール追加・分割・パッケージ再編後の記述漏れ等）を確認し、あればIssueとして起票する。
- 土: GitHub Actionsの実行履歴を確認し、実行時間が長すぎるジョブや、再実行で通ることが多い不安定なテスト（flaky test）があればIssueとして起票する。
- 日: 例外の握りつぶし、ログレベルの不適切な使用（本来warn/errorであるべきものがinfo等）など、エラーハンドリング・ログ出力の一貫性に問題があればIssueとして起票する。 / Grep で `catch (e: Exception)`・`catch (e: Throwable)`・`runCatching` を検索し、`CancellationException` を握りつぶしている箇所（キャンセルを再throwせず捨てている箇所）がないか確認する。あわせて `GlobalScope` の使用がないか確認し、あればIssueとして起票する。 / Grep で `catch` の本体を確認し、空の `catch` ブロック、ログも再throwもしない `catch`、戻り値の `Result` を使わない `runCatching` がないか確認し、あればIssueとして起票する。 / ログの一貫性として、各モジュールのロガーのライブラリ・タグの付け方がそろっているか、本番コードに `println`・`printStackTrace` が残っていないかを Grep で横断確認する。共有メモリの生データなど大量の出力になり得る値（バイト列・構造体のダンプ等）をログに出していないかも確認し、あればIssueとして起票する。 / ViewModelの `catch` ブロックが UiState のエラー状態（`MutableStateFlow` 等の更新）に反映されず、ログ出力だけで終わっていないかを該当ViewModelを読んで確認し、あればIssueとして起票する。 / `SharedMemoryReader` や WebSocketクライアントの `close()` が例外発生時にも呼ばれる構造（`use { }` や `try`/`finally` で囲まれているか）になっているかを、該当実装を読んで確認し、あればIssueとして起票する。
